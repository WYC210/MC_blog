# 按屏幕误差选择模型：Homecraft 性能优化设计

日期：2026-11-10  
状态：研究与设计，未实施运行代码。  
范围：独立评估替代技术；不替换既有方案，不改引擎、世界内容、线路或交互。

## 1. 推荐结论

推荐以“测量瓶颈 → 少量手工简化模型 → 屏幕误差选级 → 远景聚合表示”为主线，而不是首先增加大量空间批次。

LOD 指同一对象的不同复杂度版本；HLOD 指远处把一组建筑用一个低复杂度整体模型表示。只借鉴方法，不引入 Unreal、Cesium 或新渲染引擎。

核心区别是：既减少不必要的绘制，也降低仍需绘制的对象的成本。高空同时看到两个岛时，不能指望视锥剔除排除画面内的大部分内容；此时低复杂度表示更值得试验。

这不是“必然更快”的结论。现有测量能确定提交量集中在哪些对象，不能确定真实手机受 CPU、顶点处理、像素处理、上传还是内存限制。先用对照实验决定投入。

## 2. 本次项目证据

### 2.1 固定视角探测

方法：项目自带 Three.js r180；1440×900；DPR 1；晴天白天；直接指定相机并更新相关模块，连续渲染两次后读取统计。使用 SwiftShader，不测真实手机速度。外部天气、目录接口在测试上下文中返回固定结果。本次没有修改应用代码。

| 视角 | 相机位置 → 观察点 | 主画面调用 | 总三角面 | 秦岛两个主要实例批次的三角面 |
| --- | --- | ---: | ---: | ---: |
| 主岛全景 | `[-84,100,116] → [0,6,4]` | 58 | 129,436 | 55,980 |
| 秦岛正面 | `[160,18,70] → [160,7,-20]` | 13 | 152,742 | 124,800 |
| 宫殿内部镜头 | `[160,5,-23] → [160,5,-44]` | 18 | 161,486 | 124,800 |
| 秦岛远景 | `[-60,35,20] → [160,7,0]` | 54 | 130,844 | 55,980 |

这些是一次结构性探测，不是正式性能基准，也不是整条路线峰值。背景动画可能使其他位置的面数小幅变化。“内部镜头”仅代表相机位置，不代表完整入室测试。

- 秦岛正面仅 13 次调用，但秦岛两个批次占该次总三角面的约 82%。不能把所有慢场景归因于调用太多。
- 主岛全景的调用预算已经很紧，增加很多区域批次不是免费的优化。
- 秦岛近景两个批次有 9,567 和 833 个立方体实例，每个提交 12 个三角面。实例化减少调用，不会像体素网格那样自动删除家具盒子的内部面。
- 现有远景已经减到 3,840 和 825 个实例；未来收益必须以此为基线。
- 全域 `VoxelGrid` 尺寸为 306×72×172；仅 `blocks` 与 `groups` 数组合计 7,579,008 字节，不包括导航、几何、纹理。显示优化不会释放这些数据。

依据：`engine/world/blocks.js:303`、`engine/world/voxels.js:22`、`world/qin-distance-detail.js:13`、`world/qin-island.js:109`。

### 2.2 阴影路径的小型验证

用项目的 Three.js r180 创建独立场景：完整模型有 10 个实例，远景模型有 2 个实例。

- 完整模型保持 `visible=true`、`castShadow=true`，主画面 `count=0`。
- 完整模型 `onBeforeShadow` 临时设 `count=10`，`onAfterShadow` 恢复 `count=0`。
- 远景模型 `count=2`，不重复投影。
- 拦截真实 `drawElementsInstanced`，观察到实例数 `[10, 2]`：阴影绘制完整模型，主画面绘制简化模型；完整模型没有额外主画面调用。

这是现有实例批次的一条可用实现路径，不是全项目阴影方案已经完成。仍需测试昼夜、天气、屋顶隐藏、多批次和预热；普通 Mesh 不能直接照搬 `count` 方法。

## 3. 候选技术比较

| 技术 | 解决什么 | 项目代价和限制 | 决策 |
| --- | --- | --- | --- |
| 手工 LOD + 远景 HLOD | 降低仍在画面内的建筑复杂度，远景保持少量批次 | 简化模型制作、额外驻留资源、切换及阴影 | 推荐主线 |
| 静态外表面编译、相邻面合并 | 减少静态盒子的内部面，改善近景成本 | 旋转、相交、UV 复杂；展开实例会增加顶点内存 | 小范围备选 |
| `THREE.BatchedMesh` | 同材质不同几何批处理，批内对象裁剪 | 自定义 shader 和人物绑定不能直接兼容；需测试扩展降级 | 不做第一阶段 |
| 房间可见集/PVS | 室内排除不可见区域 | 门窗、开放走廊、飞行和屋顶切除使规则容易失效 | 仅严格封闭房间 |
| GPU 遮挡查询、Hi-Z | 排除视锥内被遮挡对象 | 新增查询/深度流程、异步状态和兼容性成本 | 暂不做 |
| 完整区块流式加载 | 控制常驻内存和初始化量 | 涉及导航、光照、资源和状态恢复 | 测得内存/启动瓶颈后另立项目 |

Epic HLOD 使用聚合代理模型 [R2]；Three.js 提供 BatchedMesh 对象裁剪与排序 [R4]。本项目已把很多盒子压到极少调用，不能套用“几千个独立 Mesh 合成一个”的收益案例。

## 4. 推荐架构

### 4.1 先确定成本类型

对同一路线分别进行三个独立实验：只降低渲染分辨率；只简化模型；只暂停纯表现更新。其余条件保持一致。

记录主线程更新、提交耗时、真实帧间隔、GPU 时间（支持时）、主画面/阴影调用、三角面、上传字节及实际绘制缓冲宽高。

- 随像素数下降明显改善：优先排查填充、透明叠加、水面等像素成本。
- 简化模型改善、降低分辨率影响较小：优先研究几何和提交路径。
- 暂停纯表现更新改善：排查矩阵、Canvas、缓冲上传、GC。

以上是定位线索，不是瓶颈证明，需结合 CPU trace 和 GPU 计时。GPU 测量只在支持 `EXT_disjoint_timer_query_webgl2` 时启用，异步轮询完成查询，丢弃 disjoint 结果；不阻塞等待，不把 `renderer.render()` 的 JavaScript 耗时当作 GPU 时间。[R1][R5]

### 4.2 第一版只新增一个小型远景表示

保留现有近景及已有远景规则，新增秦岛静态建筑群远景代理；实测仍有缺口才增加中景版本，不一开始给每栋建筑做三套模型。

| 表示 | 内容 | 场景 |
| --- | --- | --- |
| 现有详细表示 | 原建筑、陈设、交互、材质 | 入室、近距离、剧情、近景乘车 |
| 语义中景，可选 | 保留构型，减少重复瓦当、窗格、浮雕细分 | 中距离观景 |
| 远景整体表示 | 保留屋顶层次、门楼、主柱、主要色块及必要开口 | 从主岛看秦岛、高空广角 |

不是把岛换成一张平面图片。继续用三维低多边形模型、已有像素纹理和烘焙光照，支持侧看、俯看和不同光照。

优先简化屋顶瓦当、栏杆、窗格和雕饰。适合图案表达的内容采用小型程序纹理，不引入大型图集。洞口、显著剪影、穿行结构不能靠任意自动减面处理。

优先复用 `world/qin-architecture.js:23` 的屋顶及 `world/qin-architecture.js:41` 的栏杆构建参数，不手写一套长期不同步的建筑副本。动态人物、水车、车厢不烘进静态代理，第一版保持既有行为。

### 4.3 按屏幕误差选择，而不只按距离选择

为简化表示记录保守的世界空间误差估计 `errorWorld`，用投影和实际渲染高度估计屏幕误差：

```text
errorPixels ≈ errorWorld × drawingBufferHeight × projectionScaleY / (2 × nearestDepth)
```

`nearestDepth` 是对象包围体相对相机的保守正向深度，不是简单水平距离；临近近裁剪面或相机进入包围体时直接选择详细表示。误差估计不能冒充自动计算的精确 Hausdorff 距离。

- 从粗表示开始选择，误差超过阈值就恢复精细表示。
- 从严格的小像素误差试起，经过手机、FOV、截图确认后确定阈值，不照搬其他引擎默认值。
- 入室、交互、传送、镜头突变时当帧升级；降级可使用滞回与短暂稳定期。
- 碰撞、导航、楼板和热点独立于视觉等级，始终保留。
- 分辨率变化也影响像素误差。先固定分辨率验证 LOD，再接较慢的质量调整，避免两个控制器相互触发。
- 运行期使用预分配对象及缓存参数，不逐帧生成模型、查询 GL 状态或分配大数组。

Cesium 使用屏幕空间误差驱动层次细化 [R3]；这里只借鉴判定方法，不引入地理瓦片系统。

### 4.4 全景保持少量批次，近景按需细化

远景父级与详细子级互斥提交，不同时画两套静态模型。首个代理覆盖整个秦岛静态建筑群，先验证从主岛观察时的收益。

以后需要局部升级，再按独立地标建立少量子级。只有局部收益抵得过新增调用的子级才保留。父级替换必须覆盖同一组对象，不能重复或遗漏。现有纹理数组允许一个批次使用不同纹理层，不必每种纹理单独拆批。

明确局限：整体远景代理不能解决“站在宫殿内，其他建筑仍被巨大批次提交”的问题。若这是主要瓶颈，再试少量局部分批或严格保守的房间可见集，不能把远景收益宣传为近景问题已经解决。

### 4.5 视觉模型和阴影模型独立选择

对于现有 `InstancedMesh`，优先验证第 2.2 节的回调路径：

- 主画面显示代理时，详细批次 `count=0`，对象及祖先仍可见。
- 详细批次保留完整静态数据及完整包围体；阴影回调临时恢复投影实例范围，随后恢复主画面计数。
- 代理不重复投影；不因每次 LOD 切换重新生成太阳阴影。
- 所有 `count` 修改由唯一控制器管理，接管相关批次的旧距离写入者，避免两个模块竞争。
- 保留并组合已有回调；异常、重复阴影更新和预热结束后验证状态恢复。

完整几何本来就要保留以支持近景，不是额外复制一整套阴影模型。仍有少量对象遍历和常驻内存，不能称为零成本。r180 的零实例早退及阴影回调顺序作为版本相关契约测试。[R6][R7]

此路径暂不重写引擎。普通 Mesh、其他视图或阴影需求若无法可靠实现，先说明必要性、替代办法和引擎文件范围，获得确认后再处理。不依赖未经验证的“阴影专用层”。

### 4.6 动态更新先加脏标记，不先造全局调度框架

人物目前已独立于大部分静态投影几何，关联矩阵缓冲约 53 KB，不是每帧重传 9,567 个静态实例。

姿态没变就不标记上传，Canvas 内容没变就不重画；纯表现不可见时跳过表现计算，车辆调度和剧情继续。只有测得上传瓶颈，才评估连续更新区间或更紧凑动态批次；过碎区间也会增加调用，不为少量字节引入逐帧排序和重排。

## 5. 为什么不直接换 BatchedMesh

它是备选，不是无成本升级：

1. 大量同形立方体已经适合 `InstancedMesh`；最大静态批次只用一次调用，新 API 不会凭空消除几何成本。
2. 对象级裁剪和排序 [R4] 也有数据维护成本，需用代表性对象数量测 CPU 开销。
3. r180 缺少 `WEBGL_multi_draw` 时，相关实例多绘制路径退回逐项绘制 [R6]。本机 SwiftShader 支持扩展，不代表目标手机支持。
4. 材质直接使用 `instanceMatrix`、`iLayers`、`iEmissive`，人物依赖索引和标签；需要适配材质、拾取、光照和绑定，不是替换构造函数即可。

以后出现大量“几何不同、材质相同、需要独立裁剪”的模型，再单做原型，并测试有无扩展两种路径。

## 6. 静态表面编译：第二条实验路线

仅针对占比高的静态装饰，不把全世界实例盒子转成展开网格。

首轮只接受不会独立隐藏、移动、换级的轴对齐不透明构件，删除被同一可见性单元内其他构件完全覆盖的面。跨门窗、跨 LOD、跨屋顶切除边界的面不得据此删除。

保留颜色、纹理方向、顶面/侧面区别、像素重复密度和硬边；旋转、透明和复杂相交先跳过，不引入通用布尔运算。

即使面数下降，展开的顶点、UV、法线和颜色也可能比实例矩阵更大。比较显存估计、启动生成时间、下载大小和绘制耗时；未证明划算就保留原实例化。

## 7. 实施阶段

| 阶段 | 交付 | 通过条件 |
| --- | --- | --- |
| P0：定位成本 | 连续路线、CPU/GPU/上传报告、设备信息 | 明确优化对象，不只看 FPS 和面数 |
| P1：一个远景代理 | 秦岛静态代理，互斥显示，稳定阴影 | 有可测收益，近景不变，没有漏影、明显跳变或超预算 |
| P2：屏幕误差选级 | FOV、分辨率、俯视、横竖屏、强制升级 | 急转头/传送当帧正确，不反复切级 |
| P3：可选中景和局部细化 | 仅覆盖收益明确的地标 | 全景不回退，局部收益足够 |
| P4：可选专项优化 | 静态表面编译或动态上传优化 | 针对真实瓶颈，不被其他成本抵消 |

每阶段都包含验收，不等重构结束再测手机。P0 若发现主要问题在像素或 CPU 路径，调整顺序，不机械推进模型代理。

- `tools/check-render-budget.mjs`：未来连续测量工具，尚未创建。
- `world/qin-lod.js`：未来表示选择和唯一状态写入点，尚未创建。
- `world/qin-architecture.js`、`world/qin-island.js`：复用参数生成简化表示。
- `world/qin-distance-detail.js`：调整被新控制器接管的批次。

- 相应 Node 和浏览器回归测试。

## 8. 验收与收益目标

### 硬约束

- 常用视角不超过 60 次调用、200,000 三角面。主画面和阴影更新分别记录，不把一次 `renderer.info` 当作所有通道总和。
- 不新增实时灯光、阴影刷新频率、后处理、大型贴图；近景风格和交互不变。
- 不逐帧分配调度对象、重建几何、重排实例；新增表示在加载阶段预热。
- 记录压缩首屏体积、额外 CPU/GPU 内存和启动时间；已有超预算单列，不称 LOD 解决加载或内存问题。
- 初始化时可选择关闭优化；不保留两套完整详细世界，新增代理必须足够小。

### 实验目标，不是性能承诺

首个代理试验争取使选定远景中的秦岛静态几何提交量再降低约 30%，同时主画面调用不增加。比例只是试验继续与否的参考，不是已实现收益；视觉不合格应放弃简化。

采用依据是目标手机固定质量下的帧时间和稳定性。记录中位数、P95、P99、首次出现峰值、超 33.3 ms 帧比例，多轮独立重复，运行足够长时间观察温升。面数下降不代替真实设备收益。

必须覆盖昼夜、阴影重生成、正侧背面、俯视、门窗、屋顶隐藏、影院、人物剧情、两条过山车路线、急转头、传送、横竖屏、首次及重复恢复。
