# 空间分区、远景室内隐藏与动画休眠优化计划

日期：2026-11-10  
状态：待审阅，尚未实施本计划。  
本次交付：仅新增本文档，不修改运行代码；确认范围后再开发。

## 一、目标与结论

目标是在不改变建筑风格、行驶路线和交互规则的前提下，减少玩家看不见或远处不需要的绘制、动画计算和 GPU 数据上传。

推荐组合：

> 空间区域内继续合批 → 使用实际相机视锥裁剪 → 远处保留外观、隐藏不必要的室内细节 → 不可见的表现动画休眠 → 关键游戏逻辑独立运行。

不按东、西、南、北四个方向硬切换。区域可以按建筑群命名，但是否可见由相机实际位置、方向、俯仰、视野和区域边界共同决定。

过山车需要持续绘制整个画面。本计划优化的是每帧参与绘制和更新的内容，不是把整个应用改成只有用户操作时才渲染。

### 本阶段不做

- 不实现 MC 式完整世界流式加载、磁盘缓存或无限地图。
- 不因玩家转头创建、销毁模型，暂不卸载远处资源。
- 不做逐物体射线遮挡检测或复杂 GPU 遮挡查询。
- 不重建现有碰撞、寻路和烘焙光照系统。
- 不修改过山车线路、速度、安全限制和视角交互。
- 不承诺固定帧率提升比例；以对照测量和真实手机体验决定是否保留改动。

| 家具与零件实例化合批 | `engine/world/blocks.js` 的 `BoxBatch` | 保留，但评估过大批次的空间粒度 |

| 自适应分辨率、静态太阳阴影 | `engine/main.js`、`engine/world/stage.js` | 保留，避免掩盖对照测量结果 |

### 尚未解决的点

1. 部分实例批次覆盖较大区域，局部进入视野仍可能提交大量无关实例。
2. 秦岛现有远景规则主要按零件尺寸判断，并不识别哪些内容属于室内。
3. 宫殿屋顶已有独立批次，但部分室内、室外构件仍共用批次。
4. 各模块的可见性判断和动画暂停规则不统一，隐藏模型不一定代表停止更新。
5. 当前世界仍整体初始化；本计划不解决全域方块、导航数据的内存增长问题。

## 三、方案选择

| 方案 | 优点 | 问题 | 结论 |
| --- | --- | --- | --- |
| 四个方向整体开关 | 简单 | 斜向、俯冲、第三人称和快速回头容易漏画 | 不采用 |
| 少量空间区域＋现有合批＋视锥裁剪 | 可逐步实施，资源不需反复加载 | 需要平衡区域大小与绘制调用 | 推荐 |
| 完整区块流式加载＋卸载 | 可进一步控制大地图的驻留资源 | 涉及引擎、导航、光照、预加载和状态恢复 | 暂不实施 |

优先试点秦岛宫殿及相邻区域。不先把整个岛切成密集网格，也不同时改造所有建筑和动画。

## 四、空间分区与可见性

### 4.1 分区原则

- 以空间上接近、用途相近的建筑群为基本区域，例如宫殿、码头、园林。
- 区域内部仍按材质和阴影属性合批，避免一个装饰一个 Mesh。
- 空的区域不生成对象；跨区的大建筑先保持整体，必要时按结构拆分。
- 区域边界必须覆盖实际几何，不只检查区域中心是否位于画面内。
- 分组名称本身不会降低绘制成本；必须确保区域对应可独立裁剪的渲染批次。

### 4.2 裁剪路径

优先让各区域的 Mesh 拥有正确、紧凑的包围体，复用渲染器的视锥裁剪，不另建四向开关系统。

若需要主相机的可见性结果调度动画，另行使用复用的视锥、矩阵和包围体计算状态；不逐帧分配数组、向量、矩阵或重建几何。

主相机之外的区域不提交主画面绘制，但资源仍驻留。视锥内被墙遮挡的物体不属于本阶段通用遮挡剔除范围。

### 4.3 阴影与其他视图

- 不通过全局关闭区域 `visible` 来代替主相机裁剪，避免阴影更新时漏掉仍应投影的建筑。
- 主相机裁剪与太阳阴影相机裁剪分别处理；保持现有静态阴影策略。
- 室内或细节批次切换也可能影响投影，需检查它们是否会向外部可见区域投影，必要时保留低成本投影结构。
- 不改变小地图的地理数据、碰撞数据和热点定义；辅助视图若复用场景，需要单独确认它的可见性需求。

## 五、远景隐藏室内结构

### 5.1 语义分类

| 分类 | 典型内容 | 远景策略 |
| --- | --- | --- |
| 外部主体 | 外墙、屋顶、主要立柱、建筑轮廓 | 保留，可用现有远景细节等级 |
| 内部陈设 | 桌椅、展品、室内装饰、小构件 | 满足隐藏条件时不绘制 |
| 必要遮挡与可见结构 | 门窗后的背板、楼板、开放走廊、门洞边缘 | 根据外部可见性保留 |
| 动态或交互对象 | NPC、屏幕、剧情道具 | 独立管理，不直接混入可整体隐藏的静态陈设 |

先在构建阶段明确分类，不能仅凭尺寸小就判定为室内，也不能用包围盒相交粗略删除穿过边界的建筑结构。

### 5.2 隐藏条件与优先级

室内陈设进入远景隐藏状态，需同时满足：

1. 相机与建筑的距离或投影尺寸达到远景条件。
2. 玩家和镜头均未处于需要展示内部的区域。
3. 没有正在进行的室内交互、参观、影片或剧情要求。
4. 外部观察仍有合理的门窗背景，不会暴露空壳、透出天空或看穿地面。

优先级：交互与室内观察要求 > 屋顶隐藏后的内部可见要求 > 普通距离规则。

靠近入口时提前恢复；玩家进入、相机切入或传送到室内时立即恢复。碰撞、楼梯、楼板高度、寻路和烘焙光照数据始终保留。

### 5.3 阈值规则

- 距离优先相对建筑边界计算，而不是只测建筑中心。
- 恢复完整细节的距离小于进入远景的距离，形成滞回区间，避免反复切换。
- 大建筑、开放式建筑与封闭房间不强制使用同一阈值。
- 现有秦岛小零件规则为远于边界 100 米简化、近于 85 米恢复；这是已有规则，不直接当作室内隐藏参数。
- 新阈值在固定视角、手机横竖屏和过山车路线测量后确定，不预先承诺具体米数。

## 六、动画休眠与逻辑调度

### 6.1 分离三个状态

每个参与优化的区域或对象区分：

- 渲染状态：当前是否需要提交画面。
- 表现状态：是否需要更新姿态、粒子、材质时间和矩阵上传。
- 逻辑状态：路线、交互、计时、剧情和碰撞是否需要继续运行。

不能用一个 `active` 开关同时控制全部行为。第一阶段不改关键模拟频率，只跳过确定无副作用的表现更新。

### 6.2 分类处理

| 类型 | 视野外或远处处理 | 必须保留 |
| --- | --- | --- |
| 水花、装饰粒子、纯摆动 | 停止表现计算和 GPU 上传 | 恢复所需的少量状态 |
| 远处仍清楚可见的水车等 | 简化粒子或表现，主体运动按观感保留 | 连续、合理的姿态 |
| NPC 肢体、表情、装饰动作 | 不可见时可停止姿态计算 | 行为状态、位置及任务所需更新 |
| 过山车车厢表现 | 无人乘坐且不可见时评估跳过模型上传 | 调度、行驶、到站、呼叫与安全状态 |
| 屏幕、视频 | 不可见且无播放需求时暂停 | 用户明确播放、影院和音频需求 |
| 音乐、环境音 | 根据距离、用户设置及播放需求处理 | 不因转头就突然停止 |
| 正在参与的剧情或交互 | 按原逻辑运行 | 状态推进、输入与退出能力 |

视频隐藏不等于停止解码；需要显式管理暂停、恢复和播放位置。若涉及带音频的视频，不能把画面不可见直接当作允许暂停的条件。

### 6.3 恢复规则

- 简单循环动画可按统一时间计算当前姿态，或明确允许从暂停姿态继续。
- 有物理或交互含义的状态不得跳过必要更新；不能把装饰动画策略直接用于行驶和碰撞。
- 不累计几秒暂停时间后一次补跑大量小步，避免恢复瞬间卡顿。
- 恢复当帧先同步需要的姿态、包围体和实例矩阵，再允许绘制，避免出现旧位置。
- 动态实例保留稳定的身份映射；重分批时同步人物部件索引、拾取标签及绑定关系，不每帧重排实例。

## 七、过山车与快速视角变化

### 7.1 每帧顺序

```text
更新玩家、车辆和必要逻辑
    ↓
完成相机跟随、俯冲、环顾和第一/第三人称过渡
    ↓
确保相机世界矩阵有效
    ↓
判定当前可见性、室内细节等级和表现更新需求
    ↓
同步本帧需要显示的动态对象
    ↓
渲染
```

当前过山车在 `world/coaster-view.js` 更新相机矩阵，`world/build.js` 还会依次更新其他模块。实施时需审核是否有后续相机修改，不能假设过山车更新结束就是最终相机。

### 7.2 必须覆盖的情况

- 连续转弯、俯冲、爬升和高空观景。
- 玩家拖动镜头快速向侧后方看，以及左右反复扫视。
- 第一、第三人称切换和第三人称距离变化。
- 上车、下车、路线切换、传送、窗口尺寸变化和手机横竖屏切换。

当前视野内的内容必须当帧恢复，不等朝向稳定，不用低频定时器控制是否显示。

### 7.3 预测与资源准备

首轮所有试点资源保持驻留，优先在初始化阶段准备新增批次所需资源和材质，避免首次转头才产生昂贵创建或编译。

如测量仍发现首次切换抖动，再评估相机边缘预备范围或沿路线提前准备；这只是补充，不能依赖列车前进方向，因为玩家能突然向后看。

远近细节可使用滞回，动画调度可留适当边缘余量，但不能因此推迟新进入画面的区域显示。

### 阶段 D：表现动画休眠

- [ ] 先接入水车、室内装饰和屏幕等边界清楚的对象。

- [ ] 验证恢复不补算大段时间，不跳位、不重复触发交互。

交付：可独立启停的表现调度和恢复策略。

## 十、验收标准

### 10.1 画面与功能

| 场景 | 必须满足 |
| --- | --- |
| 面向北方或斜向东北 | 所有画面内区域完整，侧边大建筑不会突然消失 |
| 建筑远景 | 主体与轮廓保留，门窗不穿帮，无不合理空壳 |
| 走近门窗、入室、屋顶隐藏 | 需要的内部结构及时恢复，无空白过渡 |
| 过山车急转头、俯冲 | 无一帧漏画、旧姿态或区域闪现 |
| 昼夜和阴影更新 | 无建筑消失导致的漏影、光照错误 |
| 隐藏后重新出现 | 动态对象位置正确，不补算造成卡顿 |
| 空车呼叫、NPC、剧情 | 行为和交互与优化前一致 |
| 手机横竖屏 | 按实际相机视野重新计算，不沿用旧边界 |

### 10.2 性能

- 常用采样视角绘制调用不超过 60，三角面不超过 200,000；新增灯光、动态阴影和后处理为零。
- 首屏压缩加载量沿用项目小于 500 KB 的目标；补充实际测量。已有超预算需单独记录，不用删除必要功能掩盖，也不将其描述为本计划已解决。
- 不在每帧创建临时对象、重建几何或重排大批实例；不可见的纯表现对象不持续上传矩阵。
- 固定条件下分别记录帧时间中位数、P95、转头/入室切换的峰值，以及几何、纹理和可测的内存变化。
- 自动分辨率降级可能掩盖变化；比较时固定或记录实际 DPR，只比较相同渲染分辨率下的数据。
- 逐轮独立运行、预热后重复测量，不同时启动多个性能测试互相争抢资源。
- 分区后在局部观察场景应体现可测收益，高空全景不应出现明确回退；无法证明收益的拆分不推广。
- 性能目标为常用场景争取 30 FPS 及以上，但以实际手机验证为准，不用软件渲染或面数降幅替代帧率结论。

### 10.3 检查方式

- 扩展现有 Node 测试，覆盖分类、边界、滞回、强制恢复和实例身份稳定性。
- 扩展浏览器检查，记录实际提交的区域、三角面、动画调用计数和实例缓冲版本；不能只检查 `visible`。
- 运行 `npm run check:coaster`，按变更范围选择秦岛结构、影片、人物和水车回归。
- 运行 `npm run check` 并检查至少一张桌面、一张手机截图；保留外部服务错误与代码错误的区别，不屏蔽真实失败。
- 发布前由用户在真实手机上完成试乘和快速回头检查。

## 十一、主要风险与回退

| 风险 | 处理与回退 |
| --- | --- |
| 分区增加调用，反而更慢 | 减少分区、扩大区域或恢复原批次 |
| 内部隐藏导致门窗透空 | 保留遮挡结构；暂不简化有问题的建筑 |
| 快速转头、传送后显示延迟 | 当帧重新判断并同步；资源保持驻留 |
| 改批次破坏 NPC 索引与拾取 | 保留或重建稳定映射，人物专项回归不通过则不启用 |
| 动画暂停破坏剧情或车辆状态 | 只暂停表现层，关键逻辑保持原行为 |
| 阴影或辅助视图漏画 | 不用主相机结果全局隐藏建筑，独立审查投影路径 |
| 新批次首次出现造成卡顿 | 提前准备资源，测量首轮与重复路径，必要时缩减拆分 |

开发期间让空间分区、室内隐藏、动画休眠可以分别关闭，用于对照与定位；不新增面向访客的设置界面。通过构建时选择原批次/分区批次实现回退，避免为了回退同时保留两套完整模型。
